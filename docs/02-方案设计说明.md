## 棋子移动顺序修正设计（REQ-303/REQ-304，2026-10-18）

核心不再分成“数字整批先走、士兵整批后走”两段，而是新增一次统一遍历：

```text
按方向从目的边向另一端逐行/列/格处理：
  若当前格是数字块 -> 滑动、合并（每块每回合最多一次）
  若当前格是选中的己方士兵 -> 前方为空则前进一格；前方是存活敌兵则攻击
                              前方是数字/友军/死亡单位则不动
遍历结束后 -> 按数字块移动方向前方相邻士兵结算伤害（D1）
           -> finish() 统一移除死亡单位、结算击杀金币
```

因为目的边先处理，前面的士兵/数字先移动或让开，后面的士兵轮到时看到的是更新后的
棋盘；这就是“前到后”的语义。士兵攻击规则、攻击力、无反击、击杀奖励、死亡单位
阻挡到 `finish()` 都不变。

可移动数量 `gy_eligible_count(d)` 复用同一遍历，在棋盘副本上把所有己方存活士兵
标记为选中，统计实际前进或攻击的士兵数；模拟不改变真实棋盘、不生成随机块。
玩家选 N 个时，仍按初始位置到指示点的距离排序，从模拟可行动集合中取最近 N 个；
选中前缀在同一行内一定包含更靠近目的边的士兵，因此实际遍历的前后顺序与全选模拟
一致。数字合并奖励在模拟副本上计算，丢弃，不影响真实金币。

预览使用同一个 `apply_move`，因此 `gy_preview().visible` 自动反映修正后的位置和
伤害；UI 只需继续使用 `gy_eligible_count` 的数量上限，不新增预览逻辑。AI 的
`ai_generate`/`gy_simulate_move` 也自动使用新遍历；动作空间中的 count 上限会随
新可行动数变化。

性能：4~8 棋盘（默认 6×6）上每次 `gy_eligible_count` 多一次遍历；板端每 20ms 采样会对四个
方向调用，先实测，如超出预算再按 `revision+direction` 缓存，不改变语义。

非联机模式上半部分布局：左侧红色方框表示红方先手，默认标签“玩家”；右侧蓝色

现有游戏页并按原有重开流程初始化新局，AI 执红时自动开始思考。`show_page`
负责隐藏/显示准备页并维护 `prep_active`；原有 AI 搜索、REQ-316 预览和灯效路径

图标可见性，方框底色与取消/开始逻辑不变。不增加图片资源或新字库字符。

## AI 决策预览设计 REQ-316（2026-10-17）

`gy_ui_tick` 收到合法 AI 结果后不立即 `gy_commit`，而是进入预览态：移动动作调用
`gy_preview` 写入现有 `preview`、`ready`、`direction`、`selected_count`，复用与人类
倾斜完全相同的格子高亮和数量显示；放兵动作设置 `placing`、`place_column`，复用
人类放兵预览的底线列高亮。记录 `lv_tick_get()` 时间，`gy_ui_tick` 每轮检查，达到
`AI_PREVIEW_MS=500` 时调用 `gy_commit` 或 `gy_place`，然后走既有灯效/胜负/换手路径。

`ai_preview_pending` 防止重复提交；AI 回合的输入 guard 继续阻止人类倾斜/确认/放兵/
格子操作；`cancel_ai` 清除预览态，首页/重开不会在离开后落子。预览结果仍带
generation/revision 校验，提交前 `gy_commit` 会再核对 `preview.before`。使用 LVGL
tick 非阻塞等待，桌面与板端共用同一状态机；500ms 是常量，板端实测后可调整。

## 人机对战设计 REQ-315（2026-10-17）

AI 规则核心放在 `src/geyi_ai.c`/`geyi_ai.h`，只依赖 `geyi_game`，不依赖 LVGL、
RT-Thread 或文件系统，便于主机测试和后续联机复用。搜索采用 negamax + Alpha-Beta，
与想法稿要求的 Minimax 等价；同一套代码提供 `use_pruning=0` 的全量搜索开关，用于
答辩性能对比。动作空间由当前核心规则生成：四个方向上的士兵数量 1..可行动数
（无可行动士兵时允许数量 0，只移动数字块），以及金币足够时己方底线空列；每个
动作先用轻量模拟验证，非法动作不进入搜索。

规则核心增加：

```c
int gy_simulate_move(const GyGame *g, GyMove move, GyGame *next, int spawn_next);
```

它复用 `gy_preview` 的走子/合并/伤害/胜负逻辑，但不修改原局面。AI 搜索固定传
`spawn_next=0`，只换手、不生成新数字块，因此不会读取真实 RNG；真实落子仍由 UI
调用 `gy_preview` + `gy_commit` 或 `gy_place`，随机块由游戏自身生成。接受“搜索中
少一个新生数字块”的近似，后续如需增强可在根节点按空格和 2/4 概率做期望平均。

评估函数从“当前行动方”视角计算，红蓝对称，使用整数权重（详见
`docs/refs/ai-evaluation-notes.md`）：终局胜负、士兵数量、总血量、可用金币、
数字块对双方士兵的实际威胁、机动性、己方底线空位；击杀/攻击等事件只用于走法
排序，不在叶子评估中重复计分。所有启发项之和限制在终局分以下，避免材料分
淹没胜负。

搜索采用迭代加深 1..6 层，默认单次 300ms、节点数上限 200000；每层用上一层的
最佳着法优先、攻击/击杀/合并/放兵优先的走法排序；超时或收到取消标志时保留
上一层已完成的最佳着法。置换表暂不实现，先测节点数和板端耗时再决定。搜索不
使用浮点和动态分配，递归逐层复用固定大小的局面/动作工作区。

运行方式：`src/geyi_ai_task.c` 提供任务封装。开发板上创建独立 `gy_ai` 线程
（约 16KB 栈），主线程传入棋盘快照并轮询结果；AI 线程只返回动作，不直接操作
UI 或棋盘。主页/重开通过取消标志和 generation 计数丢弃过期结果；主线程落地
前再核对 `revision`。桌面版使用同步回退实现，保持同一 UI 接口。

界面沿用现有三个页面容器：模式页把原禁用的“人机对战”改为单个入口，进入
REQ-317 准备页选择先后手（左红先手默认玩家、右蓝后手默认 AI，点击方框互换）；
开始后初始化新局并记录 `ai_side`。AI 回合显示“AI 思考中”，
屏蔽倾斜、确认、放兵和格子操作；AI 落子后走与人类确认相同的灯效/结算路径。
新增界面汉字继续由 `tools/generate_ui_font.py` 生成子集，保留 OFL 许可。

| 决策 | 备选 | 选择与确认 | ADR |
|---|---|---|---|
| AI 算法 | Minimax+Alpha-Beta / MCTS / Expectimax / 规则启发式 | 学生选择 Minimax+Alpha-Beta；想法稿明确要求剪枝对比 | adr/0003-ai-minimax.md |

## 参数配置与平衡性测试设计 REQ-401~411

沿用现有纯 C 规则库与共享 LVGL 界面，新增独立参数模块 `src/geyi_config.c/.h`，
不引入文件系统、键值库或任何新依赖。

**数据模型**：用**显式结构体字段**而非通用键值数组。`GyParamSet` 逐字段列出 10 项参数，
并在 `src/geyi_config.c` 内维护一张只读**范围表**（名称、单位、下限、上限、适用模式），
界面渲染与合法性校验**共用同一张表**，避免"界面写一套、校验写另一套"。
取舍理由见 `docs/adr/0006-param-model.md`。

**与现有模块的接线（坚持最小改动）**：

- `geyi_game.h` 的 `GyConfig` 只增加**一个**字段 `spawn_interval`（10 项里唯一属于规则输入的）；
  `geyi_game.c` 把"每次有效移动固定 `spawn`"改为按 `spawn_interval` 计数，**放置士兵不计数**
  （沿用 REQ-301 的原型约定）。移动/合并/攻击/金币/胜负逻辑一行不改。
- `geyi_input.h` 增加 `gy_input_configure(GyInput*, int dir_pct, int angle_pct)`，
  把现有两处**硬编码 10% 滞回**改为读入值；**不改**四向判定算法、分段规则与 200ms 稳定窗口。
- `search_depth` 只存在于 `GyParamSet`，由界面开局启动 AI 时读取并写入 `GyAiConfig.max_depth`；本模块**不实现**搜索。

**三类配置与生效时机**：`static GyParamSet s_params[GY_MODE_COUNT]` 三份互相独立；
`gy_param_apply(mode)` 只在"**新开一局**"时调用一次，把参数转成 `GyConfig`；
板端 `gy_board` 在同一时机用当前模式的 `dir_buffer/angle_buffer` 配置 `GyInput`；
局中不再读取参数，从而保证 **REQ-407（局中改参数不改变当前对局）**。

**默认值与回归对照**：新增 4 项的默认值**取改造前的硬编码值**（生成间隔 1、方向缓冲 10%、

## 联机对战设计（REQ-501~REQ-513，2026-11-08）

> 本节依据蔡融汉 2026-11-08 给出的联机方案编写，是**设计基线**，不代表已实现。
> 代码、BLE 配置、协议编解码和双板验证均未开始；实现前必须先查 SDK v2.5.1 的
> BLE 例程与头文件，不凭记忆写 API。对应 ADR：`adr/0007-online-topology-authority.md`、
> `adr/0008-online-reconnect.md`、`adr/0009-online-preview-privacy.md`。

### 1. 拓扑与角色

![图 2-5 联机拓扑与角色](img/fig-online-topology.png)

> 图源：`docs/img/src/fig-online-topology.tex`。**隐私修正**：早期草图的 Mermaid 把
> `PREVIEW` 也画给对手，违反 REQ-507；本图与 ADR-0009 明确“对手不接收 PREVIEW，
> 房主只转发给旁观者”。实现与测试以本图和 REQ-507 为准。

- 房主：BLE 外设、GATT 服务端、房间与对局唯一权威；广播房间摘要；每房间 1 台。
- 对手：BLE 中央，镜像房主状态，只发操作意图；每房间 1 台。
- 旁观者：BLE 中央，只读镜像；0..K 台，K = 房主可接受连接数 − 1。
- 一台板同一时刻只属于一个房间；多房间 = 多台房主各自广播，不做中心服务器。
- 首版不实现局内房主迁移；等待阶段房主退出时按 REQ-505 转移或关闭房间。

**容量待实测**：SDK/芯片可接受的 BLE 并发连接数未验证（P-02）。若只能 1 条连接，
首版砍掉旁观或改中继；在实测前，旁观容量和满员广播策略都按“未定”记录，不能写成已支持。
连接态是否还能继续广播也未验证；若不能，大厅只靠 3s TTL 保留并标“未知”。

### 2. 页面与房间阶段

页面状态：

```text
单机/人机：首页 → 模式页 →（单机直接对局 / 人机准备页）→ 对局 → 结算 → 首页
联机：    首页 → 模式页 → 大厅 → 连接中(≤5s) → 房间(角色) → 对局/旁观 → 结算 → 大厅
          （房主返回大厅即解散；解散后回首页）
```

房间阶段（仅房主推进，其余端镜像）：

```text
WAIT（等待/准备） → STARTING（3s 倒计时） → PLAYING → RESULT
```

- 有人加入/退出不改变原玩家准备状态。
- 双方准备后进入 STARTING；倒计时中任一方取消准备 → 回 WAIT。
- RESULT 后房间保留约 10s 供重连者看结果；房主返回大厅即解散。
- 断线覆盖层独立于页面状态，不因重连弹窗丢失当前页面上下文。

### 3. 权威模型与同步

- 房主持有：棋盘、金币、回合、随机种子、席位/颜色、准备状态、阶段。
- 客户端只发 `MOVE_REQ`/`READY`/`SET_SEAT`/`LEAVE` 等意图，**不本地提交落子**。
- 每个合法动作后房主广播**全量快照**，带单调递增 `seq`；客户端只接受最新 `seq`，
  旧包/重复包直接丢弃（幂等）。
- 客户端可以本地倾斜预览（不发规则层提交），确认后等待快照；快照到达前棋盘不变。
- 非法/过期动作：房主回 `REJECT(reason, seq)`；客户端丢弃暂存意图并按当前权威快照重绘。
- 随机块只由房主生成并写入快照；客户端不自行生成，避免两端随机序列分叉。
- 不做增量同步；6×6 棋盘的全量快照体积小，换取实现简单和断线恢复直接。
  包长与 BLE MTU/吞吐需在实现时实测（见风险 R-026）。

### 4. 消息集合（功能级）

| 消息 | 方向 | 用途 | 幂等/错误处理 |
|---|---|---|---|
| `ADV_ROOM` | 房主→空中 | roomId、人数、阶段、观战数、协议版本 | 大厅按 roomId 更新；3s 过期移除 |
| `JOIN_REQ` | 加入者→房主 | `{role, player_id, roomId}`；role=玩家/旁观/auto | 满员/阶段不允许 → `JOIN_REJECT(reason)`；auto 由房主按当前空位裁决 |
| `JOIN_ACK` | 房主→加入者 | token、席位、player_id、房间快照 | token 绑定席位，房间存续期有效 |
| `ROOM_STATE` | 房主→房间内 | 席位颜色、双方 player_id、准备状态、观战数、阶段 | 客户端只接受房主版本 |
| `READY` / `SET_SEAT` / `LEAVE` | 玩家→房主 | 准备/取消、交换红蓝、退出 | 非法状态 → `REJECT(reason, seq)` |
| `START` | 房主→房间内 | 颜色分配、随机种子、初始快照 | 仅 STARTING→PLAYING 时有效 |
| `MOVE_REQ` | 玩家→房主 | `{seq, 方向, 数量, 放兵列}` | 非法/过期 → `REJECT(reason, seq)` |
| `SNAPSHOT` | 房主→房间内 | 全量权威状态 + 单调 seq | 客户端只认最新 seq；重复丢弃 |
| `RESULT` | 房主→房间内 | 胜负与原因 | 结算保留约 10s |
| `PREVIEW` | 玩家→房主→仅旁观 | `{side, 方向, 指示点/受影响格, seq}` | 限流；对手不接收、不回传 |
| `PREVIEW_CLEAR` | 玩家→房主→仅旁观 | 清除该玩家预览 | 确认/回中/取消时发送 |
| `HEARTBEAT` / `PING` | 房主→客方 / 客方→房主 | 1s 判活 | 10s 无包判断连 |
| `REJOIN` / `RESUME` | 客方→房主 / 房主→客方 | token + last_seq 重连、全量恢复 | token/席位不匹配拒绝 |

协议要求：消息带版本号；序列化有明确字节序和长度上限；未知消息忽略或拒绝并记录；
不得直接把 C 结构体内存当作网络包发送（避免填充/字节序/版本问题）。

#### 2026-11-09 实现修订（学生反馈后）

- **协议 v2**：`JOIN_REQ` 增加 `player_id`（uint16，芯片 UID 派生）与 `role` 的
  auto 值（2）；`JOIN_ACK` 增加自己的 `player_id`；`ROOM_STATE` 增加 host/guest 两个
  `player_id`。旧 v1 固件会被版本检查拒绝；两块板必须同版本。
- **唯一 ID 来源**：`bt_mac_addr_generate_via_uid_v2()`（失败退回 v1 / 公共地址），
  只读一次并缓存。不能用 `ble_get_public_address()` 的低 16 位作为身份：部分批次
  NVDS 地址相同，两块板都显示 `#FD5C`。
- **auto 角色**：大厅点击发 `JOIN_REQ{role=2}`；房主按“WAIT 且 player_count<2”判玩家，
  否则判旁观；即使大厅摘要滞后（刚退出一人仍显示 2/2）也不会把本可当玩家的人塞成旁观。
  显式 `watch`/旁观入口发 `role=1`，不受 auto 影响。
- **按座位 ready**：`GyNetSeat.ready` 与 `view.host_ready/guest_ready` 都按颜色更新；
  UI 用 `gy_net_app_seat_ready(color)` 分别取两个座位，禁止用“房主/非房主”或
  “按钮是否禁用”推导整块背景。准备中的座位变白，未准备保持红/蓝，空位灰色。
- **等待期退出**：WAIT 阶段没有可恢复对局，客方/旁观者断线或 LEAVE 立即释放席位并
  广播 `ROOM_STATE`，不再等 10 s；PLAYING 仍保留 10 s 重连窗口。
- **关房/转移**：房主 LEAVE 时若客人已连接 → 房主转给客人（`LEAVE_PROMOTED`），
  房间继续广播；若只有房主 → `PHASE_CLOSED` 并停止广播。客户端收到 CLOSED 只提示
  “房间不存在”，不得调用旧 promote 分支接管。
- **广播刷新**：`ROOM_STATE` 在席位/ready/阶段变化时立即广播；advertising 摘要
  使用 `is_auto_restart=1`，不在连接/断线事件里手动 start（会叠实例并
  `Create advertising failed`）。update 在 STARTING/STOPPING 被拒时只置 dirty，
  由 `gy_net_ble_poll()` 在 ADV_STARTED 后重试，最多 200 ms 一次。
- **大厅防抖**：已在大厅时再次进入不 stop/start 扫描；scan start 返回 busy 时
  1 s 后由 poll 重试，避免“再次点联机对战就再也扫不到房间”。

#### 2026-11-09 第二轮（房间循环与延迟）

- **RESULT → WAIT**：`GY_NET_RESULT_KEEP_MS` 改为 4s。超时后房间回 WAIT、
  `game_valid=0`、双方 ready 清零、result 复位；不置 CLOSED。只有房主 LEAVE 才关房。
  开局 STARTING→PLAYING 也清零 ready，下一局必须重新准备。
- **UI 路由**：游戏页在 RESULT 显示居中结算弹窗；phase 变 WAIT 时自动
  `show_page(net_room_page)`，同一房间继续。房主/客方/旁观者共用。
- **连接间隔**：客户端 `conn_intv_min/max` 从 0x60/0x80（120–160ms）改为
  0x06/0x08（7.5–10ms）。GATT 服务发现要多次 ATT 往返，旧间隔导致加入房间约 4s；
  实测降到约 0.9–1.1s。
- **关房时延**：房主关房先广播 `players=0/phase=CLOSED` 摘要并等 200ms 再停播；
  大厅收到 CLOSED/0 人立即移除，TTL 从 3s 降到 1.5s 作为兜底。实测关房到大厅消失
  约 0.2–0.4s。
- **JOIN 提前**：客户端可在 RX 特征已知时先发 JOIN（`gy_net_ble_write_ready()`），
  不必等 CCCD；ACK 由 400ms 重发兜底，CCCD 就绪后自然收到。
- **UI 可操作性**：退出/认输改为一次点击打开确认弹窗；旁观隐藏准备；准备座位绿色；
  倒计时黄底大字；对局页顶部按钮加大、底部状态条加深色底；结算用弹窗而非左下角小字。

#### 2026-11-09 第三轮（房主权威与连接资源）

- **RESIGN ≠ LEAVE**：客户端 `LEAVE` 消息带 `reason`。房主收到 `RESIGN` 只结算、
  **保留 ConnMap 与席位**；收到 `LEFT` 才释放席位并删除映射。否则结算后客方
  READY 因 `conn_find()` 为空被丢弃，表现为“房主收不到房客准备”。
- **客方倒计时**：`ROOM_STATE` 没有主机时间戳；客方首次进入 STARTING 时把
  `phase_since_ms` 设为本地 `g.now`，之后 3/2/1 由本地时钟推进。离开 STARTING
  再进入会重新起算。
- **对局页单按钮**：删除首页/大厅按钮与 `restart_button` 死代码；右上角按钮按上下文
  显示 认输/退出旁观/返回首页/退出。单机/人机结算后点击即回首页，联机结算自动回房，
  旁观退出回大厅。
- **字体子集**：`geyi_font_cn16.c` 由 UI/配置中文字面量生成；新增文案必须先运行
  `tools/generate_ui_font.py`。`run_host.py` 调用 `check_desktop_font.py` 作为门禁。
- **Remote service 生命周期**：`sibles_register_remote_svc()` 返回 0 是合法索引，
  `0xFFFF` 是槽位耗尽。记录 `conn_idx/start/end`，在断开、切换连接、重新搜索前
  `sibles_unregister_remote_svc()`；旧连接迟到的 SEARCH/REGISTER 事件按 conn_idx 丢弃。
- **RESULT→WAIT 清理**：结算结束回 WAIT 时释放已断线客人，避免“房主一直 2/2”。

### 5. 分层与线程模型

```text
net_link（BLE 广播/扫描/连接/收发包/心跳/重连定时器，独立 RX 线程 + 队列）
   ↓ 事件
net_proto（消息定义、版本、序列化/反序列化、seq 幂等）
   ↓ 结构化消息
net_room（房主权威状态机 / 客方镜像 / 旁观视图，纯逻辑，不依赖 LVGL/RT-Thread/BLE）
   ↓ 事件
UI（LVGL 主线程消费；所有 LVGL 调用只在主线程）
```

- `net_link` 的 RX 线程只做收包、校验、入队，不直接操作 LVGL 或棋盘。
- `net_room` 是纯逻辑：输入“收到的消息 + 本地意图”，输出“要发的消息 + 给 UI 的事件”；
  可在 PC 上用内存管道跑两个实例对打。
- 主线程每轮 `gy_ui_tick`/新增 `gy_net_poll` 消费队列事件，再渲染；网络线程不阻塞 UI。
- 心跳/广播定时器可由 RT-Thread 定时器或主循环时间戳驱动，具体实现以 SDK 例程为准。

### 6. 数据结构（计划）

| 结构 | 关键字段 | 说明 |
|---|---|---|
| `GyNetSeat` | `role`（房主/对手/旁观）、`color`（红/蓝）、`ready`、`connected`、`player_id`、`token` | 席位、权限与唯一身份 |
| `GyNetRoom` | `room_id`、`phase`、`seats[]`、`spectators[]`、`seq`、`last_snapshot` | 房主权威房间状态 |
| `GyNetSnapshot` | `seq`、`GyGame game`、`seat colors`、`phase` | 全量快照；`GyGame` 复用现有规则核心 |
| `GyNetMsg` | `version`、`type`、`seq`、`payload`、`len` | 协议消息头 + 负载 |
| `GyNetIntent` | `side`、`kind`（move/place/ready/leave）、`move`/`column` | 客户端意图 |
| `GyNetEvent` | `type`、`seat`、`snapshot`/`reason` | 给 UI 的事件 |

`net_room` 复用 `GyGame`/`GyMove`，不复制规则；房主只用现有 `gy_preview`/`gy_commit`/
`gy_place` 结算，客户端永不调用提交接口。

### 7. 断线、重连与判定

| 场景 | 对局 | 处理 |
|---|---|---|
| 客方瞬断 | 冻结，显示“重连中 10…9…” | 10s 内 `REJOIN(token,last_seq)` → 全量快照 → 继续；超时由房主判其负 |
| 房主掉线 | 客方冻结/重试 | 客方重试连接 10s；超时显示“对方断线”的本地终局提示。**这不是房主广播的权威 RESULT**；旁观者不跟随判负，只显示本地断线提示；恢复后不沿用该本地结果 |
| 旁观者掉线 | 不冻结对局 | 10s 内可重连拿快照；超时回大厅提示“已离开旁观” |
| 等待阶段退出/掉线 | 不判负 | 释放席位；房主退出则另一人变房主，无人则关房 |
| 对局中主动退出 | 立即判负 | “退出”二次确认后按认输处理，不等 10s |
| 结算后 | 保留约 10s | 供重连者看结果；房主返回大厅即解散 |

判定责任：在场方判缺席方负；旁观者只显示房主广播的结果或本地断线提示，不自行判定。
应用层心跳 1s、10s 无包判断连，不依赖 BLE 链路监督超时；具体定时器精度在实现时实测。

### 8. 预览私密性

- 预览是本地临时状态，从不发给对手。
- 玩家倾斜时向房主发 `PREVIEW{side, 方向, 指示点/受影响格, seq}`，限流到方向或
  指示点变化时；确认/回中/取消发 `PREVIEW_CLEAR`。
- 房主只转发给旁观者；房主自己作为对手时不渲染、不回传。

## 历史记录与计时设计（REQ-601~REQ-606，2026-11-08）

> 本节是**设计基线**，代码尚未提交；实现前需学生确认 ADR-0010 的 RAM-only 取舍。
> 对应需求：REQ-601、REQ-602、REQ-603、REQ-604、REQ-605、REQ-606；
> 测试：`docs/03` 的 TC-601~TC-606。

### 1. 范围与取舍

- v1 只做 **RAM 内最近 N=10 局** 与 **单局计时**；重启清空，不做 Flash/TF 持久化。
- 不做云端同步、跨设备历史、导出/分享、按模式筛选；这些列为拓展。
- 理由：16 MB NOR 与固件共享、无 TF 卡座；历史不是核心闭环，掉电写入与寿命风险高于收益。
  备选方案与代价见 `adr/0010-history-timer-ram.md`（**提议，待学生确认**）。

### 2. 模块与数据模型

| 模块 | 职责 | 对外接口（计划） | 代码路径 |
|---|---|---|---|
| `geyi_history` | 环形缓冲、记录写入/读取/清空、容量淘汰；纯逻辑，不依赖 LVGL/RT-Thread | `gy_history_init` `gy_history_add` `gy_history_get` `gy_history_count` `gy_history_clear` `gy_history_selftest` | `src/geyi_history.c/.h`（计划） |
| `geyi_timer` | 单局计时：开始/停止/读取；uint32 回绕安全 | `gy_timer_start` `gy_timer_stop` `gy_timer_elapsed_ms` | 可并入 `geyi_history.c` 或独立 `src/geyi_timer.c`（实现时定） |
| UI | 对局页显示 mm:ss；历史页列表/详情/空状态/清空确认 | 复用 `gy_ui_action`/`gy_ui_tick` 风格 | `src/geyi_ui.c` |

```c
typedef struct {
    uint8_t  mode;          /* 0 单机 / 1 人机 / 2 联机 */
    uint8_t  size;          /* 4..8 */
    uint8_t  result;        /* 红胜/蓝胜/平局/认输 */
    uint8_t  winner;        /* 0 红 / 1 蓝 / 0xFF 无 */
    uint16_t moves;         /* 有效行动数 */
    uint32_t duration_ms;   /* 单局时长 */
    uint32_t timestamp;     /* 开机后的秒数或 RTC（v1 可用 tick/秒） */
} GyHistoryEntry;

typedef struct {
    GyHistoryEntry entries[GY_HISTORY_CAP]; /* 10 */
    uint8_t head;   /* 下一个写入位置 */
    uint8_t count;  /* 0..CAP */
} GyHistory;
```

- 固定数组、无动态分配；写入满后覆盖最旧；`count` 最大 10。
- 记录只在“终局/认输”时写入一次；重开新局不重复写上一局；结算页重进不重复写。
- 计时用 `rt_tick_get()`/`lv_tick_get()` 的单调毫秒；用无符号差值处理回绕；
  终局后停止，不再增长。若后续需要暂停，另立需求。

### 3. 与现有模块的接线

- 规则核心在 `gy_commit`/`gy_place` 后已有 `revision`、`outcome`、`moves`；终局时 UI 读取
  `GyGame` 快照并调用 `gy_history_add`。规则核心不直接依赖历史模块，保持纯 C 可测。
- 计时在“新开一局”时 `gy_timer_start`；在 `outcome != GY_PLAYING` 或认输时
  `gy_timer_stop`；对局页每 tick 读取并格式化 `mm:ss`，不阻塞。
- 历史页只读 `GyHistory` 快照；清空需二次确认；损坏记录（字段越界）跳过并记日志。
- 联机模式只记录**本地视角**的结果与时长；权威状态仍以房主为准，历史不参与胜负。

### 4. 失败与边界

| 情形 | 处理 | 判据 |
|---|---|---|
| 记录未满 | 追加，`count++` | 顺序正确 |
| 记录已满 | 覆盖最旧，`head` 前进 | 只剩最近 10 局 |
| 同一局重复进入结算 | 不重复写 | 记录数不增加 |
| 计时 tick 回绕 | 无符号差值 | 不出现负数/跳变 |
| 字段越界/损坏 | 跳过该条并记日志 | 不崩溃 |
| 清空取消 | 不改数据 | 记录不变 |
| 重启 | 清空 | 空状态 |

### 5. 测试策略

- **主机**：`tests/test_history.c` 覆盖追加/淘汰/重复写入/清空/损坏记录/计时回绕；
  接入 `tools/run_host.py`，目标新增 1 个 target。
- **桌面 LVGL**：历史页列表/详情/空状态/清空确认；对局页计时显示。
- **板端**：完成一局后查看记录、重启后为空、计时与真实时间对照；证据入 `evidence/`。
- 在实现前，TC-601~TC-606 一律标“未实现”，不得写成通过。

## 2. 总体架构

系统由“板级驱动 → 输入/规则/AI/参数/反馈 → UI”组成，历史/计时与联机是计划模块。
完整架构、数据流与状态机见本文开头“架构、数据流与状态（2026-11-08）”的图 2-1~图 2-3；
本节只给阅读顺序：

1. 传感器与按键经 `gy_board.c` 进入 `gy_input.c`；
2. 输入状态机输出选择/确认事件，规则核心 `gy_game.c` 负责预览、提交、合并、伤害、金币与胜负；
3. AI 线程只接收局面快照并返回动作；AI 结果先预览约 500 ms 再提交；
4. 参数在“新开一局”时写入游戏/输入/AI 配置，局中不生效；
5. UI 只在主线程调用 LVGL；历史/计时与联机模块通过事件/快照与 UI 交换数据；
6. 联机时房主持有唯一权威状态，客户端只发意图、只认最新 `seq` 的全量快照。

### 4.1 软件接口

| 接口 | 输入 | 输出 | 错误处理 | 说明 |
|---|---|---|---|---|
| `gy_init` | `GyConfig`、随机种子 | 成功/失败 | 配置越界返回 0，不修改原状态 | 初始化棋盘、金币、回合 |
| `gy_eligible_count` | 方向 | 可行动士兵数 | 越界方向返回 0 | 用前到后遍历模拟，不改棋盘 |
| `gy_preview` | 方向 + 数量 | `GyPreview` 快照 | 非法动作返回 0 | 预览不改原局面、不消耗 RNG |
| `gy_commit` | `GyPreview` | 成功/失败 | 过期/不匹配快照拒绝 | 确认后走子、结算、生成、换手 |
| `gy_place` | 底线列 | 成功/失败 | 金币不足/列占用/越界拒绝 | 放兵不触发生成计数 |
| `gy_simulate_move` | 局面、动作、`spawn_next` | 新局面的副本 | 非法动作返回 0 | `spawn_next=0` 供 AI 搜索，不读真实 RNG |
| `gy_ai_choose` | 局面、AI 配置 | 动作 + 统计 | 无可行动作返回失败 | negamax + Alpha-Beta，迭代加深 |
| `gy_ai_task_start/poll/cancel` | 棋盘快照、取消标志 | 动作/状态 | 过期结果丢弃 | 板端独立线程，桌面同步回退 |
| `gy_input_update` | 角度、时间、按键电平 | 选择/取消/确认事件 | 无样本/越界取消旧选择 | 四向判定、滞回、稳定窗口 |
| `gy_param_apply` | 模式 | 成功/失败 | 非法模式返回错误 | 新开一局时把参数转成 `GyConfig` 并配置输入 |
| `gy_ui_action` / `gy_ui_tick` | UI 事件 / tick | 页面状态 | 非游戏页屏蔽游戏输入 | 首页、模式、准备页、棋盘、AI 回合 |

### 4.2 数据结构与状态机

- `GyCell`：`kind`（空/数字/士兵）、`owner`（红/蓝）、`hp`、`value`。
- `GyGame`：`cells[8][8]`、`GyConfig`、双方金币、当前回合、胜负结果、有效移动计数、
  `revision`（防止过期预览/陈旧 AI 结果）、PRNG 状态。
- `GyMove`：方向 + 士兵数量，或放兵列；`GyPreview` 保存 `before/after/visible/ready`，
  其中 `before` 用于提交前核对，`visible` 是隐藏随机生成块后的预览画面。
- `GyConfig`：`size/hp/attack/cost/merge_reward/kill_reward/spawn_interval`；
  `GyParamSet` 在此基础上增加 `search_depth/dir_buffer_pct/angle_buffer_pct` 等 10 项参数，
  由 `geyi_config` 维护范围表和三份模式配置。
- 页面状态：首页 → 模式页 →（单机直接开局 / 人机准备页 / 联机大厅）→ 对局 → 结算/认输；
  AI 状态：空闲 → 搜索中 → 预览中（约 500ms）→ 提交/取消。
- 联机状态（计划）：大厅扫描 → 连接中(≤5s) → 房间 WAIT → STARTING(3s) → PLAYING → RESULT；
  断线覆盖层独立于页面，客方 10s 重连窗口内冻结对局。
- 联机数据结构（计划）：`GyNetSeat`（角色/颜色/准备/连接/token）、`GyNetRoom`（房主权威
  阶段/席位/seq/快照）、`GyNetSnapshot`（seq + `GyGame` 全量状态）、`GyNetMsg`（版本/类型/
  seq/负载/长度）、`GyNetIntent`、`GyNetEvent`。`net_room` 复用 `GyGame`/`GyMove`，不复制规则。
- 输入状态：回中 → 方向/数量稳定 → 可确认 → 提交后要求回中；放置模式单独选择底线列。
- 历史/计时（计划）：`GyHistoryEntry{mode,size,result,winner,moves,duration_ms,timestamp}`；
  `GyHistory{entries[10],head,count}` 固定数组环形缓冲；`GyTimer` 保存开始 tick 与
  停止 tick，用无符号差值计算毫秒；终局/认输只写一次，重启清空。

## 6. 软件运行设计

- 线程：主线程负责 LVGL 与棋盘；IMU 线程约 20ms 采样并发布快照；AI 线程独立（约 16KB 栈），
  不直接操作 UI 或棋盘。所有 LVGL 调用只在主线程。联机计划增加 `net_link` RX 线程，
  只收包/校验/入队，不碰 LVGL 或棋盘；主线程用 `gy_net_poll` 消费事件。
- 同步：IMU 用互斥锁发布快照；AI 结果携带 `generation`/`revision`，主线程落地前核对，
  首页/重开通过取消标志丢弃过期结果；预览用 `lv_tick_get()` 非阻塞计时。联机用单调 `seq`
  丢弃旧/重复快照，客户端不本地提交；断线重连靠全量快照恢复。
- 时序：输入方向/数量稳定 200ms 才允许确认；AI 默认最多 6 层、单次 300ms/200000 节点上限；
  AI 预览 500ms；IMU 采样 20ms。联机计划：房间摘要 1s 广播、大厅 3s TTL、心跳 1s、
  断线判定/重连窗口 10s、STARTING 3s、结算保留约 10s；实际定时精度与 BLE 吞吐待实测。

## 8. 非功能设计

> 目标值与当前状态见 `docs/01` 的 L3 表（NFR-01~NFR-14）。本节只写设计取舍，
> 不把目标值写成实测结果。

- **性能**：4~8 棋盘（默认 6×6）；390×450 全屏目标 ≥30 fps，**板端未测**。
  输入状态机的稳定窗口为 200 ms；主机实测倾斜到预览 201–220 ms（`docs/07`），
  说明延迟主要来自稳定窗口而非采样率。AI 单次 300 ms/6 层上限；主机深度 3–5 为
  0.2–3.2 ms（`docs/07`），板端耗时未测，不能把主机时间写成板端性能。
- **资源**：规则核心固定数组、不使用动态分配；AI 线程约 16 KiB 栈；16 MB NOR 与固件共享；
  参数与历史 v1 存 RAM；历史环形缓冲固定 10 条，不引入文件系统。
- **可靠性**：预览/提交用 `revision` 防止陈旧状态；AI 结果用 `generation` 丢弃过期结果；
  联机用 `seq` 幂等、10 s 重连窗口与 token 校验；未实现看门狗和掉电恢复，
  参数/历史重启回默认/清空，属于明确的产品边界。
- **可测试性**：规则、输入、参数、AI 均可在主机编译并跑断言；UI 用桌面 LVGL 测试；
  联机 `net_room` 计划为纯逻辑，可用内存管道双实例测试；物理项必须在板上留证。
- **安全/隐私**：不采集、不上传用户数据；联机只走 BLE，token 绑定席位；仓库不存密钥。
- **可维护性**：模块边界见第 3 节；新增主机测试接入 `tools/run_host.py`；CI 运行
  `scripts/check_all.py` 与主机测试；核心模块主机覆盖率 76.2%–100%（2026-11-08，`coverage.py --min 70` PASS）；
  CI 已接入，远端 run 待确认；覆盖率是主机指标，不写成板端指标。
