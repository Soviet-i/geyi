# 棋子移动顺序采用前到后统一遍历

日期：2026-10-18。状态：已采纳（学生选择 B1 + D1），实现与真机验证待完成。

## 背景

当前核心先移动所有数字块、再移动选中士兵，且选中集合基于移动前棋盘。数字块会
看到士兵的旧位置，被数字临时挡住的士兵也不能在数字让开后移动。学生给出两例：

```text
数字2 (1,1) + 士兵 (3,1)，向右 -> 期望数字 (3,1)、士兵 (4,1)
一行 N2 B8 N2 . B8 .，向右选2兵 -> 期望 . N2 B6 . N2 B6
```

## 决策

- 采用 **B1**：按方向从目的边到另一端逐格处理数字块和选中士兵；前面的棋子先
  移动/让开，后面的棋子在轮到时基于更新后的棋盘行动，一次遍历完成。
- `gy_eligible_count` 用同一遍历模拟“所有己方士兵都选中”，返回可行动士兵数；
  玩家仍按初始位置距离选取最近 N 个。
- 伤害采用 **D1**：所有棋子移动结束后，按数字块移动方向前方相邻士兵结算伤害；
  仍可伤害己方。
- 士兵攻击规则不变：一步一动作、固定攻击力、无反击、不进入敌方格子；死亡单位
  到 `finish()` 才移除，同一回合继续阻挡。

## 备选

| 备选 | 放弃原因 |
|---|---|
| A：仅把选中士兵移到数字之前 | 能修第一个例子，但第二个例子中被数字挡住的士兵仍无法被选中/移动 |
| B2：按最近 N 个己方士兵选择，不管当前是否被挡 | 可能选中永久卡住的士兵，和想法稿“不可移动的不计入”不一致 |
| C：单独在移动后重新判定阻挡士兵 | 逻辑与 B1 重复且更容易不一致；B1 的统一遍历已包含动态腾格 |
| D2：只有数字滑动中真正撞到才伤害 | 学生期望两个士兵最终都变 B6，说明采用最终前方相邻伤害；D2 更复杂且不符当前期望 |

## 后果

- `gy_eligible_count` 的结果会变化，输入数量映射、UI 数量显示、AI 动作空间都会
  随之变化；需要板端重新观察角度/数量手感。
- 现有精确位置/可移动数量测试需要按新规则更新，并新增两个固定局面；不能为了让
  测试通过而放宽判据。
- AI 的搜索结果会变化，需要重跑 62 条断言、30 手自对弈和剪枝基准。
- 预览和实际落子共用核心，不需要新增 UI 预览代码。
- 每次可行动数计算多一次 6×6 遍历；板端性能待实测，必要时按 revision/direction
  缓存。
