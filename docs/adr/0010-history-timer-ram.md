# ADR-0010: 历史记录与计时 v1 采用 RAM 环形缓冲

- 状态：**已被 ADR-0013 取代（2026-11-12 学生决定改用 NOR + FlashDB KV 持久化）**
- 日期：2026-11-08
- 决策人：蔡融汉（原提议）；2026-11-12 郑瑞杭确认持久化方案
- 协助：Claude Code / deepseek-v4-flash
- 关联需求：REQ-601~REQ-606

## 背景

首页已有“历史记录”入口但一直禁用。课程要求未完成功能要明确标注，不能留一个点了没反应的
死按钮；同时产品需要“复盘”能力。历史/计时模块尚未提交代码，需要先决定：

1. 历史记录存哪里：RAM、NOR Flash、TF 卡，还是配套端；
2. 保存多少条、满了怎么淘汰；
3. 单局计时用什么时基、是否支持暂停/跨重启。

硬件约束：16 MB NOR 与固件共享、**无 TF 卡座**、无电池；参数 v1 已经选择不持久化。
课程也明确“是否需要断电保持在立项明确，不默认追加文件系统”。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. RAM 环形缓冲（N=10） | 实现最简单；无 Flash 写入/寿命/掉电问题；主机可完全测试；不影响核心闭环 | 重启/掉电清空；不能跨天累计 | **提议采用** |
| B. NOR Flash 持久化（键值/文件） | 重启保留；可做长期统计 | 需评估与固件共享的占用、擦写寿命、掉电写入、格式升级；增加故障面 | 首版不做；若学生要求，另立 ADR |
| C. TF 卡存储 | 容量大；可导出 | 课程板**无 TF 卡座**；需外接与文件系统 | 不可行 |
| D. 配套端/云端 | 可长期保存、可视化 | 需要额外端与服务；涉及隐私与联网；超出当前闭环 | 列为拓展 |

## 决策（提议）

选择 **方案 A**：

- `GyHistory` 使用固定数组 `entries[10]` + `head/count` 的环形缓冲；满后覆盖最旧；
  **不使用动态分配**。
- 记录字段：模式、棋盘大小、结果、胜方、总步数、时长 ms、时间戳；每局终局/认输只写一次。
- 计时用单调 tick 的毫秒差值（`uint32` 无符号回绕安全）；新开一局开始，终局/认输停止；
  不做暂停，不做跨重启累计。
- 历史页提供列表、详情、空状态、清空（二次确认）；损坏记录跳过，不崩溃。
- 产品说明明确写“历史记录重启清空”；不把 RAM 记录宣称为永久保存。

理由：历史不是核心胜负闭环，首版优先“可测试、无掉电风险、不影响固件”；10 条足够
支撑课内复盘与答辩演示。持久化的收益不足以抵消 Flash 写入/寿命/格式升级的复杂度。

## 后果

- 正面：无 Flash 写入；主机可用固定序列完全测试；内存占用固定且小；与参数 v1 的
  “RAM-only”策略一致。
- 负面/代价：重启清空；不能做跨天长趋势；用户需要被明确告知。
- 需要同步修改：`docs/01` REQ-601~606；`docs/02` 历史/计时设计；`docs/03` TC-601~606；
  `manifest.yaml` 的 `design.key_decisions`。

## 待确认/待定

- **学生是否接受“重启清空”**；若不接受，改为方案 B，并先评估 NOR 占用与掉电写入。
- 时间戳 v1 用“开机后秒数”还是 RTC 日历时间；若用 RTC，需确认板载 RTC 是否已校准。
- N=10 是否足够；可在不改变模型的前提下调整常量，但需同步 TC-603 的边界。
- 联机历史只记录本地视角；是否需要记录对手/房间号，待联机实现后决定。
