# ADR-0015：WAIT 阶段房主转移后，旁观者跟随新房主

- 状态：已采纳（学生 2026-11-13 选择方案 B；同日真机确认房主主动退出场景）
- 日期：2026-11-13
- 决策人：项目负责人（本次会话明确选择）
- 关联需求：REQ-510、REQ-505
- 关联问题：R-083

## 背景

WAIT 阶段双人房里房主退出/掉线时，客人会接管为新房主，`room_id` 不变并继续广播
（`gy_net_app_leave` 的 `LEAVE_PROMOTED`，以及 2.5 s 断线接管兜底）。玩家侧已经
工作正常。

但旁观者的重连目标仍然是**旧房主的 BLE 地址**：`gy_net_app_tick` 在
`g.dropped` 后反复 `gy_net_ble_connect(g.join_addr, ...)`，而 `join_addr` 是旧
房主；10 s 后 `gy_net_room_client_host_lost()` 判定旁观者丢失，UI 回房间页/大厅，
显示“断线重连 → 已离开旁观”。新房主用同一 `room_id` 广播，但旁观者从未重新扫描。

这不是最近远程合并引入的回归：`f738dbc`（2026-11-09）同时加入了“双人房主退出转给
客人”和 `spectator_lost` 自动退出，但没有让旁观者跟随；`410e8f8`（2026-11-08）的
UI 还没有 `spectator_lost` 自动退出。最近三个联机提交没有改这条路径。

## 备选

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 房主退出/掉线即房间消失 | 语义最简单，和“房主是唯一裁判/房主重启房间消失”一致 | 推翻学生 2026-11-09 明确要求的“双人房主退出转给客人”；玩家侧已工作的接管被砍掉；房主误触退出整房解散 |
| B. 保留房主转移，旁观者扫描同 `room_id` 跟随新房主 | 保留玩家接管；旁观者继续观看；`room_id` 已由 `promote_client` 保留 | 需要新增旁观者扫描/重加入状态；旧广播/容量/断电时序要处理；文档/测试要补 |
| C. 旁观者立即回大厅，手动重新加入 | 比 B 简单 | 大厅点房间走 auto 角色；新房主只有 1/2 时会被当成第二个玩家，不是旁观者；大厅没有旁观入口 |

## 决策

采用 **B：保留房主转移，旁观者跟随新房主**，并且按阶段处理：

- **WAIT + 有客人**：
  - 收到房主转移的 `ROOM_STATE`（新 host 颜色、`player_count=1`、WAIT）时，旁观者
    停止对旧地址的 REJOIN，清空扫描队列，扫描同一 `room_id` 的新广播。
  - 找到新 host 后连接并发送 **`JOIN_REQ{role=SPECTATOR}`** 的全新 JOIN（新 token）；
    不能沿用旧 REJOIN token，因为 `gy_net_room_promote_client()` 已清空新房主的
    旁观列表。
  - WAIT 阶段旧 host 会立即释放旁观席位，旧 token 不能 REJOIN；因此任何匹配到
    的 host（包括旧地址）都用全新的 `role=SPECTATOR` JOIN。由转移状态触发的
    扫描会丢弃旧 host 的残留广播，只等新房主。
  - 10 s 内找不到、或 JOIN 被拒（满/阶段不允许），提示加入失败原因后 2s 回大厅。
- **链路直接丢失（房主断电，没有转移消息）**：
  - 先按原重连逻辑尝试旧地址 3 s（与客人接管窗口一致）；WAIT 下旧席位已
    释放，最终仍是全新 SPECTATOR JOIN，不是 REJOIN。
  - 仍失败且最后已知状态是 WAIT、`player_count>=2`，切换到同 `room_id` 扫描。
  - 最后已知状态不是 WAIT，或没有客人可接管：保持原 10 s 重连窗口，超时回大厅。
    这样不会把旁观者自身的瞬断误判成房主离开。
- **PLAYING/STARTING/RESULT 或没有客人可接管**：沿用原有 10 s 重连窗口，超时回大厅。
  不立即踢出，是为了避免旁观者自己的 BLE 瞬断被误判成房主离开；代价是房主真的
  断电时多等最多 10 s。
- **UI**：跟随期间房间状态显示“房主已转移 正在重新加入...”，不再显示 10 s 倒计时。

## 后果

- 新增旁观者跟随状态：`spectator_scan / spectator_follow / spectator_scan_at` 与
  旧 host 地址快照；`gy_net_app_spectator_following()` 供 UI 查询。
- 扫描结果由专门的 `spectator_follow_poll()` 在主循环中消费，避免被大厅
  `lobby_drain()` 先吃掉。
- 需要主机测试覆盖：转移状态触发、扫描筛选、非 WAIT 拒绝、旧 host 残留广播丢弃、JOIN_ACK 清理；
  三端物理测试覆盖房主主动退出、房主断电、连续两次迁移、旁观容量。
- 现有“旁观者确认房主丢失时先 abort 再回大厅”的文档需要改写；大厅/房间状态文案
  需要新增“房主已转移”。
- 2026-11-13 学生真机确认：房主主动退出后客人接管、旁观者保持“观战 1 人”
  （`evidence/net/20261113/spectator_follow/`）。房主直接断电、旁观者自身 RF 瞬断、
  连续两次迁移、双旁观者容量仍未留证。
- 风险：旧 host 关播前的 stale 广播（同 `room_id`）、无转移消息路径 3 s 后才
  开始扫描、新房主旁观容量满、旧席位 10 s 保留与 fresh JOIN 的交互。实现中必须
  重试/回退，不能让旁观者卡死。
- 已知限制：连续两次迁移依赖旁观者已收到“客人加入”的 2 人 `ROOM_STATE`；若该包
  丢失，本地 `player_count` 停在 1，第二次迁移可能只能等 10 s 回大厅。三端验证
  必须覆盖“故意漏收一次 2 人状态”的情形。
