# ADR-0009: 联机预览可见性

- 状态：已采纳
- 日期：2026-11-08
- 决策人：蔡融汉　协助：Claude Code / deepseek-v4-flash
- 关联需求：REQ-507

## 背景

单机/人机对局里，倾斜预览只显示在本地屏幕上。联机后，预览需要经过房主：
如果直接把玩家预览广播给房间内所有人，对手就能看到对方正在选的方向和数量，
等于泄露操作意图；如果完全不显示远程预览，旁观者又看不到对局细节。需要决定
预览的发送、转发和渲染边界。

## 备选方案

| 方案 | 优点 | 缺点 | 对需求/风险的影响 |
|---|---|---|---|
| A. 预览只发房主，房主只转发给旁观者；对手不接收、不回传；客户端只认自己的预览 | 对手看不到，保住操作私密；旁观可看双方；实现边界清晰 | 需要按角色路由；旁观 UI 要叠加双方颜色；多板验证成本 | 满足 REQ-507；路由错误风险 R-027 |
| B. 预览广播给房间内所有人 | 实现最简单；旁观和对手都能看到 | 对手可偷看，破坏对局公平；与“预览是本地临时状态”冲突 | 不选 |
| C. 完全不转发远程预览，旁观也看不到 | 私密性最好；实现最少 | 旁观只能看落子结果，观战体验差；不满足旁观需求 | 不选 |
| D. 延迟转发（落子后才给对手看） | 对手不能实时偷看 | 对手仍能看到已发生的选择；延迟窗口难定；对旁观也无收益 | 不选 |

## 决策

选择 **方案 A**：

- 预览是玩家本地临时状态，从不发给对手。
- 玩家倾斜时发 `PREVIEW{side, 方向, 指示点/受影响格, seq}` 给房主，限流到方向或
  指示点变化时；确认落子或回中/取消时发 `PREVIEW_CLEAR`。
- 房主只转发给旁观者；房主自己作为对手时不渲染、不回传。
- 客户端只接受“来自自己”的预览，远程预览丢弃。
- 旁观者用双方各自颜色叠加两个预览。
- 验收判据：对手屏幕看不到、旁观屏幕看得到，需多板物理验证。

理由：这样既保住对手之间的操作私密，又让旁观者有可看的对局细节；路由规则简单，
可以写成 `net_room` 的纯逻辑测试，再用双板验证真实屏幕。

## 后果

- 正面：对手无法通过预览偷看；旁观体验完整；预览不进入权威状态，不增加快照负担。
- 负面/代价：房主需要按角色路由；旁观 UI 要区分双方颜色；路由错误会泄露（R-027）。
- 需要同步修改：`docs/01` REQ-507；`docs/02` 联机设计；`docs/03` TC-507；
  `manifest.yaml` 的 `design.key_decisions`。

## 待实测/待定

- 双板 + 旁观设备的实际屏幕验证；没有旁观设备时只能验证“对手看不到”，不能宣称
  “旁观看得到”已通过。
- 预览限流的实际频率与 BLE 带宽；必要时调整限流条件，但不得改成广播给对手。

## AI协作

agent 根据学生方案整理 A~D 备选；学生明确选择“只转发旁观、对手不可见”。agent 补充了
限流、`PREVIEW_CLEAR`、客户端只认自己预览的测试判据，均来自学生方案；未自行扩大可见范围。
