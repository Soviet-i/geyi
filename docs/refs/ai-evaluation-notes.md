# AI 评估函数笔记与评审

来源：学生原始笔记 `D:\15957\College\Class\3_1\软件体系结构\minimax.md`
（2026-10-17）。以下“原始思路”保留原意，“评审建议”为开发搭档补充，
权重是初始候选值，尚未经过平衡性测试。

## 原始思路

1. 结局：胜利 +100000，失败 −100000，平局 0。
2. 奖励项：
   - 金币 `n × w_金币`；
   - 士兵数量 `n × w_士兵`；
   - 士兵血量 `n × w_血量`；
   - 击杀 `n × w_击杀`；
   - 攻击造成的敌方血量损失 `n × w_血量`。
3. 惩罚项：
   - 敌方士兵数量/总血量；
   - 我方即将受到的伤害、预计失去的士兵；
   - 我方被卡位、无法移动的士兵。
4. 未确定：中立数字块的数值、其他因素。

## 评审建议

1. **事件项不要和状态项重复计分。** “击杀”“攻击造成伤害”在子局面中已经
   体现为敌方士兵数量、血量和金币的变化；如果叶子评估再单独加一次，等于
   同一件事算两遍。建议只把击杀/攻击作为**走法排序**信号。
2. **敌方材料不需要单独惩罚。** 直接用“我方 − 敌方”的士兵数量、总血量差，
   不要另加“敌方士兵/血量”负分。
3. **终局分必须压住所有启发项。** 保留 ±100000，但启发项之和要限制在
   ±99999 以内；否则材料分可能淹没胜负。
4. **中立数字块不按数值直接加到某一方。** 它不属于任何一方，价值体现在：
   - 沿某个方向能撞到谁、造成多少实际伤害；
   - 能否与同值数字合并（获得金币、变大）；
   - 阻挡双方士兵/数字的位置价值。
   建议按“每个方向上第一个会被撞到的士兵”计算
   `min(数字值, 士兵剩余血量)`，再乘折扣权重；不要简单把全盘数字值加总。
5. **金币要打折。** 4 金币能放一个兵，但需要己方底线有空位，放兵还会结束
   回合；底线满时金币价值更低。建议按可用空位截断有效金币。
6. **补充机动性、底线空位、被卡士兵、数字合并潜力。** 前两项比“被卡”更有
   价值；“被卡”有时也是保护，权重应低。
7. **评估函数必须对称。** 从“当前行动方”视角计算，红蓝使用同一套公式；
   不要写死 AI 是红方。
8. **使用整数。** 板端避免浮点；数字块相关的量要设上限，防止指数值溢出。

## v0 权重表（待调参）

从当前行动方视角计算；“我方/敌方”由 `g->turn` 决定。

| 项 | 初始值 | 说明 |
|---|---:|---|
| 终局胜/负 | ±100000 | 平局 0 |
| 士兵存在 | ±500/个 | 胜负只看士兵存活，权重高 |
| 士兵血量 | ±20/点 | 与 `config.hp` 相关 |
| 金币 | ±100/枚，按可用上限截断 | 4 金币约等于 0.6 个满血兵 |
| 数字块威胁 | ±10 × 实际可造成伤害 | 只看该方向第一个士兵，按 `min(数字值, 血量)` |
| 数字合并潜力 | +30/对 | 合并给金币并增大数字；首版可先不做 |
| 机动性 | ±10/个合法动作 | 只算当前行动方，避免每个叶子复制对手状态 |
| 己方底线空位 | ±30/个（金币足够时） | 放兵潜力 |
| 被卡士兵 | −20/个 | 权重低，卡位有时也是保护 |
| 击杀/攻击事件 | 0（只用于排序） | 避免与子局面重复计分 |

## 调参计划

- 固定局面测试：一步获胜、避免明显自伤、能击杀时优先攻击、非法动作过滤。
- 剪枝对比：同一局面、评估、深度，只切换 `use_pruning`，记录节点数与耗时。
- 自对弈：在主机上用不同权重跑短局，观察是否出现明显短视/循环；板端只用
  最终候选权重验证响应时间。
- 不把初始权重写成“平衡性通过”；正式规则和参数仍需团队/组长确认。
