# 与 AI agent 协作开发指南

本项目鼓励（并要求）用 AI agent（Claude Code、Codex 等）完成从需求、设计、编码到测试文档的全过程。教师侧也会用 agent 评审你的材料。所以你的工作要让**另一个 agent 和教师都能读懂、能核验**。

## 1. 分工：人负责什么，agent 负责什么

| 环节 | agent | 你（学生） |
|---|---|---|
| 需求/设计起草 | 起草、提备选、查漏 | 判断、取舍、定稿、拍板 |
| 编码与重构 | 实现、跑测试、修错 | 读懂代码、抽查、否决越界实现 |
| 文档同步 | 保持 PRD/设计/测试一致 | 确认变更的原因与影响 |
| 提交与日志 | 起草信息与日志 | **逐项确认真实性** |
| **真机验证** | 给出操作清单、分析证据 | **亲自做、亲自留证据** |
| **关键决策** | 提供 ≥2 个备选与权衡 | **决定** |

agent 不能烧录板子、看屏幕、摸马达、焊东西。凡是需要物理世界的，必须你来做，agent 到这里必须暂停。

## 2. 开始前：让 agent 读规则

仓库根目录有 `CLAUDE.md` / `AGENTS.md`，Claude Code、Codex 会自动读取。其他工具请在会话开头粘贴：

```
请先阅读仓库中的 AGENTS.md、docs/guides/git-workflow.md 和 docs/00-项目计划与里程碑.md，
然后用不超过 8 行复述：当前里程碑、最近一篇开发日志的要点、你将遵守的提交/日志/物理验证规则。
```

## 3. 一次开发会话的标准流程

```
开工 → 计划(你确认) → 文档先行 → 测试 → 实现 → 验证 → 小步提交 → 收工(日志+检查)
```

1. **开工**：让 agent 汇报当前状态（里程碑、未完成项、最近提交），你纠正它理解错的地方。
2. **计划**：让它先列计划再动手；超过半小时的工作必须有计划。
3. **文档先行**：要新增功能，先在 `01` 写 REQ、`02` 写设计、`03` 写 TC，再写代码。
4. **测试驱动**：先有失败的测试，再实现。禁止改测试期望值去“凑通过”，除非需求变了并记录在案。
5. **小步提交**：做完一小块就 `/commit`（或按 git-workflow.md 提交）。
6. **收工**：`/devlog` 写日志 → `python scripts/check_all.py`。

## 4. 物理验证暂停协议

遇到下列事项 agent 必须暂停：固件烧录与启动、传感器实测读数、屏幕 UI 实际效果、马达/震动手感、焊接与组装、蓝牙/BT PAN 联网。

流程：

1. agent 给出编号操作步骤、需要的证据与建议文件名（带日期）；
2. agent 明确说“需要你在真机验证并回传证据”，**停止**；
3. 你实际操作，把原始证据（日志/照片/截图）放入 `evidence/<里程碑>/`，告诉 agent；
4. agent 阅读证据，判断结论，登记 `manifest.yaml` 与 `04-测试报告.md`；
5. 以 `hw(...)` 类型提交，`验证:` 写证据路径。

> 没有条件做的验证（如没有示波器）不要编证据，在 `known_issues` 如实说明。这不扣分；编造证据按学术诚信处理。

## 5. 防止 agent 带偏你的检查清单

| 常见问题 | 你怎么发现 |
|---|---|
| 虚构 API/寄存器/SDK 函数 | 要求它给出所在头文件或文档链接，自己 `grep` 验证；编译不过先别信它的解释 |
| 为了“通过”改预期/放宽判据 | 看 `git diff docs/03* `与自检代码；判据变更必须有需求变更依据 |
| 声称“已测试通过”但没运行 | 要求贴出命令与输出；自己再跑一次 |
| 编造实测数据 | 实测值必须有 `evidence/` 里的原始文件 |
| 越界实现（加了没要求的功能） | 对照 REQ 清单看 diff |
| 悄悄改文档/规则文件 | `git diff` 看 `CLAUDE.md`、`course.config.json`、`scripts/` 是否被动过 |
| 提交信息夸大 | 逐条核对“改动/验证”是否属实 |

出现这类情况时，**记入 `06-风险与问题台账.md` 的“AI 相关风险记录”和当天日志**——这是研制总结“AI协作总结”的核心素材，也是加分项（说明你在认真把关）。

## 6. 可复制的提示词

### 6.1 开工

```
读取最近 3 篇开发日志、docs/00 当前里程碑、git log -10 和 git status，汇报：当前状态、未完成事项、
建议本次目标（最多 3 项）。不要修改任何文件，等我确认。
```

### 6.2 需求→设计→测试

```
我要新增功能：<一句话>。请先只修改文档：在 docs/01 增加 REQ-xxx（含可验证的验收标准），
在 docs/02 增加对应设计条目，在 docs/03 增加 TC-xxx。完成后运行 python scripts/check_trace.py。
给出 2 个设计备选及权衡，等我选择后再继续。
```

### 6.3 按需求实现（编译由 agent 做，上板由你做）

```
为 <模块> 实现 <功能>。约束：先阅读 docs/01 中对应 REQ 与 docs/03 中的 TC，以及 SDK 里相关的官方例程；
不要凭记忆编造 SDK 的 API，用到的函数和宏要给出所在头文件；实现后运行 python scripts/build_firmware.py 并贴出输出。
不要加入需求之外的功能。上板结果你无法判断，完成后停下来，告诉我需要我提供哪些证据。
```

### 6.4 收工

```
今天收工。请：1) 运行 python scripts/new_devlog.py(--update)；2) 依据今天的 git 记录与我口述的内容，
逐节起草开发日志（不确定的地方向我提问，不要编造）；3) 展示草稿等我确认；4) 确认后写入并提交；
5) 运行 python scripts/check_all.py 汇报结果。
```

### 6.5 评审前自检

```
按 docs/00 的 M<n> 交付物清单做提交前自检，运行 python scripts/check_all.py --final，
列出缺口表（已完成/缺口/建议动作/需要我本人完成的事），不要用虚假内容填补缺口。
```

## 7. 会话记录

把完整、未编辑的会话记录导出到 `logs/`（见 `logs/README.md`），在 `manifest.yaml` 的 `dev_agent.session_log_path` 引用。你的纠正、agent 的错误都留着——它们说明你**真的在做**。
